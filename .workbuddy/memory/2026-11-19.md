# 2026-11-19

## 下载卡片文件大小改为上游动态获取（方案 A：运行时 + 1h 缓存）

### 背景

`lib/downloads.ts` 里 `SIZE` 常量硬编码 15/8/12 MB，与真实资源差距巨大
（实测 v0.4：zip 58,194,396 B / apk 48,898,538 B / exe 83,128,320 B，
即 55.5 / 46.6 / 79.3 MB），属展示错误而非仅维护性问题。

### 关键事实（下次别再踩）

- **Gitee API v5 不返回 `size`**，只给 `browser_download_url` 和 `name`；
  但 Gitee 下载地址 HEAD 能拿到 `Content-Length`。
- **GitHub Releases API 直接给 `assets[].size`**，一次请求覆盖整个 tag，
  未认证限额 60/h（按出口 IP，Vercel 共享 IP 有风险）→ 支持可选 `GITHUB_TOKEN`。
- **WAN `v0.4` 与 LAN `lan_v0.4` 的文件大小不同**（LAN 27.7/36.1/51.9 MB），
  所以大小必须按 tag 解析，不能全局按文件名缓存一份。
- `.next` 构建输出显示 `/download`、`/lan-download` 为 SSG + `revalidate 1h`，
  fetch 的 `next.revalidate` 不会把页面变成 dynamic。

### 改法

- 新增 `lib/download-sizes.ts`：`resolveSizes(items, tag, locale)`
  1) GitHub API 取 `assets[].size`（`next: { revalidate: 3600, tags }`）；
  2) 缺失项对**访客实际会点的主镜像**发 HEAD 读 `Content-Length`（`cache: 'no-store'`）；
  3) 仍失败 → 该文件名不出现在返回 map 里。
  全程 `AbortSignal.timeout(4000)` + try/catch，永不 throw。
- `lib/downloads.ts`：删 `SIZE`；`sizeBytes` → `fileName`（作为 join key）；
  导出 `WAN_TAG` / `LAN_TAG`；`formatSize(bytes?: number|null): string|null`，
  未知返回 `null`；改为 1 位小数并去掉 `.0`（46.6 MB / 12 MB）。
- `DownloadCard`：新增可选 `sizeBytes` prop，chip 与按钮后缀均在 `sizeLabel`
  为 null 时不渲染（不显示"未知"/"0 B"）。
- 两个下载页各自 `await resolveSizes(downloads, WAN_TAG, locale)` 并透传。

### 验证

- `tsc --noEmit`、`next build` 通过。
- 生产服实测：`/zh/download`、`/en/download` 渲染 46.6/55.5/79.3 MB；
  `/zh/lan-download` 渲染 27.7/36.1/51.9 MB。
- 单测式验证：`formatSize(undefined|null|0)` → `null`；
  全部 URL 失效时 `resolveSizes` 返回 `{}` 且 822ms 内完成（不阻塞渲染）。
